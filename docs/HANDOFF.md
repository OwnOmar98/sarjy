## 1. The assignment, in brief

Source: Sarj's take-home brief ("Building Sarjy").

**Build:** a voice-controlled assistant that listens and responds, remembers prior conversations with the user, and has access to at least one external API (creativity counts).

**Deploy:** accessible via the web, live and try-able.

**Present:** a 5-minute presentation to the full Sarj team, with a Loom/PDF/markdown shared beforehand so the meeting can be mostly questions.

**Explicitly open-ended.** The brief lists ~10 optional directions (video avatar, language switching, latency, quality/fidelity, telephony, guardrails, multimodal, presentation style, cost, integrations, multistep workflows) and says to pick a few, not all.

**Rubric — what's actually graded:**

- **Communication**: daily updates (even "no time today" counts), asking when blocked, an early draft PR, a PRD/TDD written _before_ building, and how the final work is presented.
- **Ownership / practicality / speed**: how the problem was approached given the constraints, how the code was thought about.

There is explicitly no single correct solution. This document exists partly _for_ the communication half of that rubric — it's the evidence trail.

## 2. What we committed to (see `docs/PRD.md` for the full reasoning)

Three pillars from the brief's list, plus three not on the list:

- **Latency** — instrumented per stage, shown live on a HUD.
- **Language switching (AR/EN)** — including mid-sentence code-switching, measured rather than just claimed.
- **Cost** — real per-minute unit economics at 100/1k/10k users.
- _(added)_ Arabic TTS text normalization, graceful degradation (voice has no spinner — silence is the failure mode), a small CI eval harness.

**Non-goals, stated up front:** no telephony, no video avatar, no multimodal image input, no production auth (anonymous per-browser identity only).

**Stack:** Nuxt 4 + Vuetify (web) · LiveKit Cloud (transport/SFU) · LiveKit Agents in Python (VAD → turn detection → STT → LLM → TTS) · Postgres+pgvector and Redis (memory) · Groq (STT/LLM) · Gemini TTS by default, ElevenLabs Flash v2.5 as a swap-in.

Full architecture, latency budget, memory design, and cost model: `docs/PRD.md`. Design direction and brand decisions: `PRODUCT.md`.

## 3. Current state — what's actually working

Manually tested end to end, repeatedly, including live conversation in both languages:

- Browser connects to a LiveKit room, agent joins, greets the user in English and mentions it speaks Arabic.
- Full multi-turn conversation holds context correctly (e.g. remembers the user's name mid-conversation).
- Language handling works in both directions — tested with English and Arabic input in the same session.
- Clean disconnect via a Stop button; the agent session tears down correctly on the backend.
- CI is green on both `web` (typecheck + build) and `agent` (lint) for push and PR triggers, plus a third workflow (`eval.yml`) running the real latency scorecard on every push to `main`.
- Local dev infra (Postgres+pgvector, Redis) is live via `npm run docker:up`, schema applied, and connectivity verified end to end using the exact connection strings the agent uses.
- **Deployed and live**, not just locally: web on Vercel (https://sarjy-eight.vercel.app), agent worker on LiveKit Cloud (auto-deploys on push to `main` via `.github/workflows/agent-deploy.yml`), Postgres on Neon, Redis on Upstash. Verified with a real end-to-end browser session against the deployed stack, not just local dev.

**Latency pillar — done, not stubbed:**

- `agent/latency.py` publishes real per-stage timings (endpointing, stt, memory, llm_first_token, tts_first_byte, total) to the room's `"latency"` data topic and logs the same to `turn_traces`; `LatencyHud.vue` renders both the live per-turn waterfall and a session-wide p50/p95 table, computed client-side off real values only.
- `eval/run.py` — a CI eval harness that drives 4 synthesized fixtures through the actual production `entrypoint()`/`SarjyAgent` in a real LiveKit room (not a re-implementation), reporting real p50/p95 per stage. Two real bugs had to be found and fixed before it produced any data at all (see §4).
- `inference.TurnDetector()` wired explicitly (was already the implicit default, but shouldn't silently change out from under us on an SDK upgrade); Redis-backed TTS phrase cache for the one genuinely fixed string in the codebase (`_FALLBACK_MESSAGE`, now also `_MISSED_SPEECH_MESSAGE`); a one-time region probe confirmed Groq/Gemini are both served close enough to the deployed agent's `us-east` region that moving regions wasn't worth it.

**Implemented and verified live — `agent/tools.py`:**

The full "prayer time → availability → book → confirm" chain from `docs/PRD.md` §1 is written and registered on `SarjyAgent`:

- `get_prayer_time` — real call to the Aladhan API (no key needed), method 4 (Umm al-Qura, standard for KSA). Takes `date` as `"today"`, `"tomorrow"`, or an ISO date, resolved in `Asia/Riyadh` — so "بعد المغرب بكرا" (after Maghrib tomorrow) resolves correctly without needing the LLM to do date arithmetic itself. Returns a machine-parseable ISO datetime alongside the human-readable answer, so the model can feed it straight into the next tool call.
- `check_calendar_availability` / `book_calendar_event` — our own Postgres table (`calendar_events`, added to `db/schema.sql`), not real Google Calendar. Real Calendar writes need OAuth2 or a service account, not the plain `GOOGLE_API_KEY` we have — a deliberate scope call (discussed and agreed), not a shortcut hiding from anyone. The brief only requires one external API and `get_prayer_time` already covers that.
- `cancel_calendar_event` — added after a real user tried to cancel a meeting and got "I don't have the functionality to delete events." Matches by `user_id` + exact `start_time` (optionally narrowed by `title` when more than one event shares a slot); returns a clear "no event found" or "more than one matches, ask which" rather than guessing. The LLM never sees a raw event id — it's expected to call `list_calendar_events`/`check_calendar_availability` first to learn the exact time, same pattern as booking. `SarjyAgent`'s instructions require the same confirmation discipline as booking before calling it (state which specific event, wait for a real yes/no, never cancel in the turn the request was first made) — cancellation is just as irreversible as booking, arguably more so. **Verified live, both paths**: seeded a real event, asked to cancel it — the agent called `list_calendar_events` first, asked for confirmation, did not cancel yet; a real spoken "yes" then correctly called `cancel_calendar_event` and the DB confirmed the row was gone. Separately verified the decline path with a fresh seeded event: a real spoken "no" (STT rendered it as a repeated, slightly garbled "لا، لا تقوم بحقها..." but the LLM still understood it correctly) produced zero tool calls beyond the initial `list_calendar_events` — the event was still there in the DB afterward, confirming the safety-critical property (given this session's whole thread on STT yes/no mishearing risk) that a decline never accidentally deletes anything.
- `user_id` never reaches the LLM as an argument — tools read it via `RunContext.userdata`, set from `AgentSession[str](userdata=user_id, ...)` in `main.py`. `SarjyAgent.on_user_turn_completed` was refactored to read the same `self.session.userdata` instead of its own constructor arg, so there's one source of truth for "whose session is this" across memory and tools.
- New shared `agent/db.py` holds the asyncpg pool now that two modules (`memory.py`, `tools.py`) need it — `memory.py` was refactored to use it instead of its own private pool.

**Verified live:** real Aladhan call for tomorrow's Maghrib in Riyadh; full check→book→check-again cycle against the real local Postgres (correctly reports free, books, then correctly reports the conflict). Confirmed the worker boots clean with tools registered.

**Implemented, partially verified — `agent/memory.py`:**

Fact extraction (Groq, cheap model), Postgres/pgvector storage, cosine-search retrieval, and Redis caching are all written and wired into `main.py`:

- `on_user_turn_completed` calls `memory.retrieve()` per turn and injects results into the LLM's chat context.
- The `conversation_item_added` event (user-role messages only, sidestepping the barge-in-truncation question entirely) fires `memory.extract_facts()` + `memory.store()` as a background task.
- Embeddings go through the new `agent/embedding_adapter.py` — a provider-agnostic wrapper (same pattern as `tts_adapter.py`) currently backed by Gemini's `gemini-embedding-001`, pinned to 768-dim to match `db/schema.sql`. Deliberately decoupled from `tts_adapter.py`/TTS provider choice — unrelated concerns that happened to both touch Google's API.
- Cross-session recall required a real per-browser identity: `web/app/composables/useSarjyRoom.ts` now mints and persists a UUID in `localStorage`, sent as `identity` to `/api/token` — previously it was `user-${Date.now()}` (a fresh, un-persisted id every session), which would have made cross-session recall silently never work despite the code otherwise being correct. `token.get.ts`'s fallback also now generates a real UUID (`facts.user_id` is a Postgres `uuid` column with an FK to `users`).

**Verified live, with real Gemini embeddings (credits topped up):** `extract_facts()` against real Groq (correctly extracts durable facts, drops transient ones like "what's the weather"); `store()`/`retrieve()` against the real local Postgres+pgvector+Redis with real `gemini-embedding-001` calls — confirmed genuine semantic search, not keyword matching: querying "when is my recurring meeting?" correctly ranked the Sunday-meeting fact first, "what color do I like?" correctly surfaced the color fact. Confirmed the agent worker boots clean with all the new imports/event wiring.

**Not yet verified:** an actual browser round-trip (state a fact in one session, start a new one, agent recalls it by voice) — everything above was a script-level test against the same functions `main.py` calls, not a live LiveKit session. Also still missing: wiring `retrieve()`'s output into `groq.STT(...)` as vocabulary hints (§5's "memory feeding ASR" — the second thing that pillar promises, not done yet).

## 4a. Day 4 — issue triage, corrections, and what shipped

**Read this section before trusting §4's older entries.** Day 4 started by re-checking the
open issues against installed `livekit-agents` source rather than against this document's
own prior conclusions, and two long-standing beliefs recorded here did not survive.

**Corrections to earlier entries in this document:**

1. **"Early speech is silently dropped during AEC warmup, and `transcription_timeout` is
   what covers it."** Half right. `agent_activity.py`'s `push_audio` substitutes silence
   **only on the STT path** — the source comment is explicit that "VAD, AMD and the
   interruption detector keep receiving the real frame". So VAD fires normally during
   warmup, the timeout arms normally, and the net does work — but the mechanism written down
   here (audio withheld from everything) was wrong.
2. **"An empty transcript could leave a turn unanswered."** Ruled out. `stt.StreamAdapter`
   drops empty results (`elif not t_event.alternatives[0].text: continue`) before they reach
   `audio_recognition.py` at all, and the watchdog is disarmed only by a final transcript
   with non-empty text — so an empty result leaves the net armed rather than defeating it.
   Since both configured STTs are one-shot and wrapped in `StreamAdapter`, this is the path
   every transcript in this app takes.

Both corrections narrow issue #4 rather than solving it: with those two ruled out, the
remaining explanation for the "zero pipeline events" anomaly recorded further down §4 is
that **VAD never reported speech at all**, and the prime suspect is Krisp BVC — which sits
upstream of VAD and is the main difference between "VAD in isolation" (fires) and "VAD in
the pipeline" (nothing). Untested; one live session with debug logging settles it.

**One genuine gap found and closed:** `_arm_transcription_timeout` returns early while
`_turn_transcript_received` is still set from the previous turn, and that flag is only
cleared during end-of-turn cleanup — so a second utterance arriving inside that window has
no net at all. `main.py` now runs a `user_state_changed`-driven watchdog on a longer delay
(4.0s vs the SDK's 2.5s, so the SDK always gets first refusal) that speaks the existing
missed-speech prompt for a turn nothing else covered.

**Shipped this session:**

- **`undo_last_action`, plus a required read-back after every write** (`tools.py`,
  `main.py`). This is deliberately _not_ another attempt to detect a false confirmation —
  §4's own record shows four such attempts failed, including Whisper's `no_speech_prob`
  reading 0.0 on the exact clips that hallucinated. It accepts that a wrong write can happen
  and makes it reversible: the agent must now say back what was written, and the last
  booking or cancellation can be reversed for 15 minutes, by row id, so a later booking in
  the same slot can never be the one removed. A cancellation undo restores the original row
  id. `propose_cancellation` now also carries `duration_minutes` so an undone cancellation
  comes back intact.
  **Deliberately not shipped, and why it matters:** the analysis in `docs/ISSUE_ANALYSIS.md`
  §2 recommends three things for the confirmation risk. Only the undo/read-back one shipped.
  The second — a code-level evidence gate on `confirm_pending_action`, refusing a write when
  the confirming turn had near-zero speech duration — is the same idea as the duration-based
  guard §4 records as built-then-removed, and re-attempting it on the same evidence base would
  repeat that mistake. It stays deferred until `--safety` produces both a false-accept rate
  and a duration distribution for genuine confirmations. The third — requiring a
  content-bearing confirmation rather than a bare yes/no — is a product call about
  conversational naturalness, not a purely technical one, and should also be measured rather
  than assumed.

- **Greeting language selection bug.** §4's `turn_traces` entry closed with "left as-is
  since nothing downstream reads this field" — but the dynamic-greeting work added later
  _does_ read it, via `_detect_language(" ".join(known_facts))`. That function is
  Arabic-first by design, so a single Arabic proper noun among otherwise-English remembered
  facts greeted an English-speaking user in Arabic. Switched to
  `detect_code_switch().primary_language`, which counts tokens. Unit-tested, including a
  test that asserts the two detectors still disagree on the bug case — if they ever stop,
  the fix has silently become a no-op.
- **Memory → STT vocabulary hints** — §5's second memory promise, previously unbuilt. Now
  wired through the supported `AgentSession(stt_context_options=STTContextOptions(keyterms=…))`
  API rather than any private hook, fed by proper nouns extracted from remembered facts.
  Honest scope: it reaches whichever STT advertises the keyterms capability, which Groq does
  not — so today it applies to the OpenAI fallback only. The initial `memory.retrieve()` also
  moved ahead of session construction (it now feeds both this and the greeting) and is
  wrapped in a try/except, so an unreachable Postgres or Redis costs memory rather than the
  whole conversation.
- **Memory extraction of bare "want" + a universal quantifier** — the one case §4 left
  deliberately unresolved. `_EXTRACT_SYSTEM_PROMPT` now states that "all"/"every"/"كل" makes
  even a bare "want" a standing rule, phrased as a shape rather than a worked example
  specifically because §4 records a concrete example in this prompt being echoed verbatim
  onto unrelated input.
- **Arabic currency normalization** — the last untouched category from PRD §2. Both writing
  orders (`SAR 250` / `250 SAR` / `$250`), Arabic-Indic digits, decimal separator spelled
  out. 12 unit tests. Never exercised end-to-end, since no feature produces currency text.
- **Whitespace-insensitive title matching** in `propose_cancellation` — closes the
  "TeamSync" vs "Team Sync" brittleness §4 records as pre-existing.
- **The safety half of the eval harness.** `eval/run.py --safety` (or `EVAL_SAFETY=1`) runs
  six multi-turn scenarios and asserts on real database state: after a booking request
  followed by silence, room tone, or a spoken refusal, `calendar_events` must be empty for
  that user; a bare single word must produce at least one user-turn trace. Each scenario
  uses a fresh identity, and a failing scenario's rows are deliberately left behind for
  inspection. Kept off the default push path — it is multi-turn and slow — but it is what
  turns issues #1/#2 from "occasionally" into a rate.
- **`agent/tests/`** — 31 unit tests over the pure logic touched here. `ruff check` and
  `ruff format` clean across `agent/`.

**Added after the first review pass** (a code review of the above raised two points; one was
a documentation error, one exposed a real gap):

- **Per-turn `speech_duration_proxy` instrumentation.** The review's position on the deferred
  evidence gate was "get real numbers from `--safety` before attempting it again" — correct,
  but the harness as written emitted only PASS/FAIL, so those numbers would never have
  existed and the decision would still have been un-makeable. Checking why the earlier
  attempt had to use a proxy at all: **`livekit-agents` exposes no per-turn VAD speech
  duration on the success path** — `speech_duration` rides only on
  `UserTranscriptionTimeoutEvent`, the failure path, and the full public event list
  (`voice/events.py:298-314`) carries nothing else. That is the root cause of
  "uncalibratable", not a mistake in the earlier attempt. `main.py` now logs a
  `speech_duration_proxy` stage per turn and `--safety` prints the per-scenario range, so the
  `false_confirm_*` and `short_utterance_*` distributions can be compared directly.
  Deliberately **recording only** — nothing reads it to decide anything; building the
  instrument is not building the heuristic. Named `_proxy` because it measures wall-clock
  between `user_state_changed` transitions and so includes Silero's `min_silence_duration`
  hangover; the offset is constant across both populations, so the separation is measurable
  even though the absolute values are not. Calling it `speech_duration` would have recreated
  exactly the false precision that sank the previous attempt.
- **Unbounded growth in `_pending` / `_last_action`** — found while re-reading the session's
  own new code, not raised by the review. Both are module-level dicts keyed by `user_id` in a
  long-lived worker process, and both only ever shrank on `pop`, so a user who proposed and
  never confirmed (or confirmed and never undid) left an entry behind permanently.
  `_last_action` was introduced this session, so half of it was self-inflicted. Now swept
  lazily on propose/confirm/undo via `_expire_stale()`. Behaviour is unchanged — both were
  already TTL-checked on read — so this is purely a leak fix. Unit-tested, including that the
  TTL boundary is not swept early (it must stay consistent with the tools' own `>` checks)
  and that the implementation materialises the key list before deleting, since the naive
  version raises `RuntimeError`.

**Verification status, stated plainly:** unit tests pass, lint passes, imports and the
`STTContextOptions`/`AgentSession` API compatibility were checked against the installed
package. **No live room, no real STT call, no browser session.** The two non-speech eval
fixtures (`silence.wav`, `room_tone.wav`) are generated and committed; the five new speech
fixtures need a Gemini key before `--safety` can run at all — which also means the new
`speech_duration_proxy` has never produced a value.

**One lint note, deliberate:** `ruff` flags `eval/run.py`'s import block as unsorted. It is
pre-existing and must stay that way — those imports have to follow the `sys.path.insert` that
makes `agent/` importable. `npm run lint:agent` scopes to `agent/` only, so this is outside
the checked set; "fixing" it would break module resolution.

## 4. Known issues

**Fixed this session** (kept brief — see git history for detail):

- SSR layout jump from `v-app-bar`'s layout registration → switched to `v-toolbar`.
- Nuxt/Vuetify `useLayout()` naming collision → resolved via module's `prefixComposables` option.
- `google.TTS()` used the wrong Gemini API (needs GCP service-account creds) → switched to `google.beta.GeminiTTS()`, which reads a plain API key.
- Unimplemented tools were registered on the agent, so the model attempted real tool calls and leaked raw `<function=...>` syntax as spoken output → tools unregistered until `tools.py` is actually implemented (now done, re-registered — see §3).
- A low-confidence turn combined with default preemptive generation produced a reply that silently never played → disabled `preemptive_generation` until it's validated against the multilingual turn detector.
- ElevenLabs TTS crashed even with the key set, because the LiveKit plugin reads a differently-named env var (`ELEVEN_API_KEY`) than ours (`ELEVENLABS_API_KEY`) → fixed by passing the key through explicitly.
- **Agent never rejoined after Stop → Start.** Root cause: the room name was hardcoded (`"sarjy"`), and LiveKit's automatic agent dispatch fires once per _new room_, not per participant join — reconnecting to the same room name could leave the second session with no agent at all. Fixed by minting a unique room name per session.
- CI `build` failing on `npm ci`: `web/package-lock.json` had drifted out of sync with `package.json`. Regenerated and verified (`npm ci` + `npm run typecheck` both clean).
- **Arabic input transcribed as English gibberish.** Root cause, found from a real browser session's debug log: `groq.STT(model="whisper-large-v3-turbo")` defaulted to `language="en"`, `detect_language=False` — every utterance got forced through Whisper as English regardless of what was spoken, so Arabic speech came back as phonetic English nonsense (e.g. "Sargeesho daun il-mufatlan" for what was almost certainly "سرجي، شو لوني المفضل؟"). This was the exact gap the `TODO(day 2): swap STT/LLM/TTS per request by language` comment already flagged, just not yet done. Fixed by setting `detect_language=True`. **Re-tested live, confirmed active** — a follow-up session's log shows `"language": null` on transcripts (Whisper is now genuinely detecting per-utterance, not defaulting) instead of the previous hardcoded `"en"`. Note: Groq's non-`whisper-1` models don't return the detected language back through this plugin's non-verbose response format, so the multilingual turn detector still can't select its per-language (`"ar"`) threshold from this — no worse than before (which was also always wrong-tagged "en"), but not the win it could be either. Left as-is; a livekit-plugins-openai limitation, not something fixable from our side without forking the plugin.
- **Model called tools unprompted with fabricated arguments; separately, wrote a fake tool call as spoken text.** First log: right after a clean English turn ("my favorite color is blue"), the model spontaneously called `check_calendar_availability` with a made-up date (`2024-03-16`, nobody asked). Tightened instructions to require a clear request before calling a tool and to ask instead of inventing details. **Re-tested live — didn't fully hold**: a second session showed a _different_ failure mode instead, the model writing `<function=check_calendar_availability>{...}</function>` as literal spoken/displayed text rather than a real tool call (nothing was actually booked). This is a known Groq/`llama-3.3-70b-versatile` function-calling reliability quirk, not something a prompt alone reliably prevents. Fixed properly at the source: `SarjyAgent.llm_node` now wraps the default node in `_strip_leaked_tool_syntax()`, a streaming buffer that cuts output the instant `<function=` appears in the text — real tool calls live in `ChatChunk.delta.tool_calls`, a separate field from `.content`, so this can't touch a correctly-formed call. Unit-tested against a real Groq streaming response (byte-for-byte passthrough, unaffected) and two synthetic leak cases, including the marker split across chunk boundaries. **Not yet re-verified against a live recurrence** — the failure is nondeterministic, so absence in one more test wouldn't prove much either.
- **"Sarjy" consistently misheard as "Sergey"/"Sergei," including inside Arabic transcripts** (e.g. "سرجي" → "سيرجي," an anglicized respelling baked right into the Arabic script). Root cause found via a live test: `groq.STT(...)`'s `prompt` was English-only ("Hi, I'm Sarjy, your voice assistant.") — Whisper's prompt biases both vocabulary _and_, on short/ambiguous audio, the detected _language_ toward whatever the prompt is written in. Fixed with a bilingual prompt (English + Arabic sample carrying "Sarjy" in both scripts). **Verified with a real, controlled test**: synthesized the same Arabic phrase via Gemini TTS, ran it through Groq's actual transcription endpoint with the old vs. new prompt — old prompt produced "سيرجي" (wrong), new prompt produced "سرجي" (exact match), reproducibly, on both `whisper-large-v3-turbo` and `whisper-large-v3`.
- **Tested `whisper-large-v3` (full model) vs. `-turbo` for AR language-ID/accuracy** — a real, measured pillar comparison, not a guess. Synthesized matched Arabic test clips (one full sentence, three single ambiguous words: "نعم," "المغرب," "بكرا") via Gemini TTS and ran each through both models on Groq's actual endpoint. Result: both models mis-detected language equally often on short/ambiguous single words (tagged "German"/"Polish," not even English) — a real Whisper limitation on short audio, not something either model choice fixes. But on a wrong-language detection, turbo tended to _stay in Arabic script_ ("نام."), while the full model tended to _romanize into Latin_ ("Nam.") — reproducing the exact "speaks Arabic, writes English" complaint that prompted the test. Full model measured zero accuracy win and costs more latency (docs/PRD.md §2), so reverted to `-turbo`. Worth a line in the presentation's language-switching section — it's real before/after data on a real product decision, exactly what that pillar commits to measuring rather than claiming.
- **Expanded the STT prompt with short, common product vocabulary** (yes/no, day words, the five prayer names) after the model-comparison test above raised a separate question: could the prompt improve _word_-level accuracy on short utterances, not just the language bias it already fixed? Tested the same way — matched clips, old vs. new prompt, same model (`-turbo`) — across the six short words plus the control sentence. Result: fixed one real word-level error ("نعم" — "yes" — was heard as "نام," meaning "slept"; now correct) with zero regressions on the other five. Doesn't touch the wrong-language-_tag_ issue (a separate acoustic sub-task the prompt doesn't influence), which is already established as mostly harmless since nothing in the codebase reads that tag.
- **Tested OpenAI's `gpt-transcribe` (with its `languages: ["ar","en"]` constraint) against Groq turbo** — a real head-to-head, prompted by asking whether the STT can be told explicitly it only needs to consider two languages (Groq/Whisper's API can't — binary lock-one-language-or-full-~100-language-detect, no subset mode). `gpt-transcribe` supports exactly that language-list constraint via `livekit-plugins-openai`. Ran all eight test clips through both, same bilingual/vocabulary prompt on each side, matched pairs. Result: the language-list constraint made zero measurable difference (identical output with/without it, tested twice); Groq was consistently faster (300–500ms vs. 440ms–3.4s); and `gpt-transcribe` regressed on the single clearest test case — the one full clean control sentence — reproducing the exact "سرجي" → "سيرجي" bug already fixed on the Groq side, plus dropping a possessive pronoun, _despite_ the identical prompt. No accuracy win, real latency cost, one real regression. Stayed on Groq. `OPENAI_API_KEY` is in `.env` (funded, $5 credit) in case this is worth revisiting with real mic audio later, but nothing in the codebase currently uses it — no `stt_adapter.py` was built, since the evidence didn't support switching.
- **Transcript panel stopped auto-scrolling partway through a turn.** `TranscriptPanel.vue`'s scroll watcher only fired on `entries.length` changing, but most updates are an existing entry's `.text` growing in place as interim STT/TTS-synced segments arrive (`useSarjyRoom.ts` updates by segment id, not by pushing a new array item) — so once a turn's text outgrew the visible panel, the rest stayed hidden until the next new turn. Fixed with a `{ deep: true }` watch on the entries array itself.
- **`connect()` had no error handling at all.** A denied mic permission, a bad token, or a dropped `room.connect()` all failed silently — the user was stuck on the "Start talking" button forever with zero feedback, and a double-click during the async connect window could fire two concurrent connection attempts on the same `Room`. Uses the same hold-back-a-tail technique as `_strip_leaked_tool_syntax` so a pattern split across two streamed chunks still gets caught. **Caught and fixed a real bug during testing**: the first version always prepended "الساعة" inside the time-formatting helper, producing a duplicated `"الساعة الساعة 2 ظهرًا"` when the surrounding text already said it (the common case, e.g. `"الموعد الساعة 14:00"`) — fixed by moving that word to only the one caller (a combined date+time with no natural leading context) that actually needs it. **Verified four ways**: unit tests on the string function directly (dates, times, combined datetimes, Arabic-Indic digit variants, pass-through of non-matching text — all correct); a mocked-synthesis test confirming the cache path for the two fixed phrases is completely unaffected, a single-chunk pattern gets normalized, and the _same_ pattern deliberately split across two chunks still gets caught identically; and a final live TTS→STT round-trip on the normalizer's actual output, repeated 3 times to check for non-determinism — day and month recovered correctly every time, the year digit was occasionally mis-heard by STT (2026/2021/2020 across 3 runs of identical input), the same class of minor residual noise already characterized throughout this session's testing, nowhere near the complete gibberish of the raw format. Currency wasn't addressed — no live feature in this app currently produces currency text, so there's nothing real to test or normalize yet.
- **Built, then removed, a scoped confirmation-safety guard for the نعم-hallucination risk — kept here for the reasoning trail, not because it's active.** The STT prompt already reproducibly hallucinates the literal word "نعم" onto silence/noise (documented above and in task #26/#27's findings), and two upstream fixes were tested and rejected: removing نعم/لا from `_STT_PROMPT` regresses real "نعم" transcription 100% reproducibly; raising `silero.VAD`'s `min_speech_duration` to filter short noise bursts also silences real short words entirely (tested live). Built a narrower, downstream mitigation instead: tracked an approximate per-turn speech duration (via `user_state_changed` transition timestamps — no public per-turn VAD-duration signal exists on the success path) and injected a caution system message when a reply was both short (≤3 words) and suspiciously fast (<0.5s). Calibrated against one real measurement (a spoken "Yes" at 0.598s), verified via direct condition tests to fire/not-fire correctly at the boundaries. **Removed after further research showed it wasn't actually well-founded**: asked what production ASR/voice-agent systems do about this class of problem — the real, purpose-built signal is Whisper's own `no_speech_prob`/`avg_logprob` confidence scores (via `verbose_json`), not audio duration. Confirmed Groq's `whisper-large-v3-turbo` does return these fields, then tested them directly against the exact silence/noise clips that hallucinated "نعم" earlier: **`no_speech_prob` was `0.0` on every one of them, including the hallucinated cases** — the model is fully confident in its hallucinated output, a documented, unsolved failure mode of confidence-based Whisper hallucination filtering generally, not something specific to our setup. With the "correct" industry signal also failing to catch this on our own reproduced case, the duration-based guard had no honest justification left — it added real false-positive risk on genuine short confirmations for a benefit that was never actually verified. Removed entirely (`_last_speech_duration`, `_SHORT_REPLY_WORD_LIMIT`, `_MIN_PLAUSIBLE_SPEECH_DURATION_S`, the `user_state_changed` tracking, all gone from `main.py`). The نعم/لا live-pipeline anomaly from calibrating this (real events firing 0 pipeline events at all) is still open — see below — but is no longer blocking anything since this guard no longer exists to calibrate. Residual risk is accepted as documented: VAD already rejects these specific synthetic clips before they'd reach STT in the live pipeline, and the existing read-back-then-wait-for-confirmation flow matches real IVR/voice-agent best practice — further mitigation would need a technique nobody's actually solved yet, not more heuristics layered on an unproven signal.
- **Unexplained anomaly found while calibrating the guard above, not yet root-caused.** The exact same `نعم`/`لا` test clips that transcribe correctly via direct Groq API calls (task #26/#27) and that trigger `silero.VAD` cleanly in isolation (`start_of_speech` fires) produced **zero events at all** — no `user_state_changed`, no `user_input_transcribed`, nothing — when played through the real live pipeline (`fake_job_context` + real `AgentSession`, same harness pattern used successfully for dozens of other tests this session, including a longer "Yes" clip and a full sentence that both worked correctly in the same test run). Not yet explained: whether this is specific to very short/quiet TTS-synthesized single-word clips failing some full-pipeline threshold that raw VAD-in-isolation doesn't have, a `fake_job_context`/`RoomIO` timing quirk unique to sub-second clips, or something else. Ruled out Groq's rate limit as the cause (reproduced with `LLM_PROVIDER=openai` forced). Worth investigating separately — if this reflects real production behavior rather than a test-harness artifact, it would mean genuinely short/quiet single-word utterances can silently fail to reach STT at all in some cases, a more fundamental gap than the hallucination risk this guard targets.
- **Every single `turn_traces` row had `language="unknown"`.** Root cause, confirmed by calling Groq's raw transcription API directly (not just reading the plugin source): Groq's `whisper-large-v3-turbo` _does_ support language detection — `response_format=verbose_json` returns a real `"language"` field — but `livekit-plugins-openai` (which `groq.STT` subclasses, since Groq's endpoint is OpenAI-compatible) only requests that richer format for the literal model name `"whisper-1"`, which Groq never uses. So `ev.language` was empty on every single turn regardless of our own config, not an inherent Groq limitation as the code previously assumed. Fixed with a fallback: a script-based heuristic off the transcript text itself (Arabic Unicode presence → `"ar"`, else Latin letters → `"en"`) when the provider doesn't report one — scoped to exactly the two languages this project supports, not general language ID. **Verified live** through a real STT round-trip: language now correctly tags `"ar"` across every stage of a real Arabic turn. **Known, accepted limitation**: the Arabic check runs first, so any Arabic character in a code-switched utterance tags the whole turn `"ar"` even if it's mostly English — a coarse "was Arabic present" flag, not proportional/dominant-language detection. Left as-is since nothing downstream reads this field yet (not the eval harness report, not the HUD) — not worth building for a dimension with no consumer.

**Known, not yet fixed:** — _historical as of Day 4. Two entries below have since been
addressed (the bare-"want" memory extraction gap, and the coarse language tag, which turned
out to have acquired a consumer) — see §4a. `docs/KNOWN_ISSUES.md` is the current state;
this list is the trail that led there._

- **Three-mode language policy (task #24) doesn't fully hold on pure-English input.** Tested the new instructions directly against the LLM with clean text, bypassing STT/audio entirely so the only variable was the wording. Real improvement in 4/5 cases — most notably genuine loanword code-switching now shows up where it couldn't before (mixed input with no easy Arabic equivalent, e.g. "بدي أسوي reschedule للmeeting", got back "أي meeting تقصد" — an Arabic sentence naturally carrying an English loanword, not possible under the old strict-mirroring instructions). One case didn't fully comply: a purely English input ("I want to book an appointment tomorrow at three") still got a reply that opened with Arabic filler ("أكيد") before switching to English, rather than staying English throughout the way "mostly English → reply in English" intends. Likely the model's own default filler habit, not a flaw in the wording — tightening it further to force strict compliance risks reintroducing the rigid word-by-word mirroring the policy exists to avoid. Left as-is; revisit only if it turns out to matter in practice, after tasks #25–#30 (memory normalization, STT prompt test, benchmark, language metadata layer, deterministic booking logic, dynamic greeting) are done.
- **Memory extraction (task #25) had a genuine gap unrelated to code-switching — 3/4 fixed, one case left deliberately unresolved.** "I want all my meetings to be after 5pm" extracted as `[]` (nothing) in pure English, pure Arabic, and mixed phrasing alike — a general fact-extraction sensitivity issue, not caused by the code-switching normalization change. Isolated the actual cause: phrasing structure, not content — declarative statements ("I prefer...", "I always...") extracted fine, but "want"/"should"/"never"/request-shaped phrasing didn't. Added explicit guidance to `_EXTRACT_SYSTEM_PROMPT` (a stated preference is durable regardless of phrasing — want, should, always/never, please-only-ever — judge by whether it describes an ongoing pattern, not the literal wording), with a concrete durable-vs-one-off example pair. Re-tested against 6 phrasing variants: fixed "Please only book meetings after 5pm", "All my meetings should be after 5pm", and "I never schedule meetings before 5pm" — all now extract correctly, with the genuine one-off/small-talk filter still intact (no regressions). **Still doesn't extract**: the original repro case itself, "I want all my meetings to be after 5pm" (and its Arabic equivalent, "بدي كل meetings تكون after 5") — bare "want" without an explicit always/never/should marker still reads as ambiguous between a standing rule and a one-time request, which arguably it genuinely is in natural speech. Decided against another prompt-tuning pass for now — real risk of chasing diminishing returns on an inherently fuzzy case. Revisit after the remaining tasks (#26–#29) are done and decide then whether it's worth another try.
- **Caught and fixed a real hallucination while building task #25, same mechanism as the STT prompt bug below.** The first version of the normalized memory prompt included a third few-shot example, `"prefers meetings after 5 PM"`, alongside the two pre-existing ones. At `temperature=0`, that exact string got echoed verbatim onto a _completely unrelated_ input ("بدي أعمل booking بس بعد الظهر دايماً" — "I want a booking, but always after Dhuhr," nothing about 5 PM or meetings) on every one of 3 repeat runs. Same failure shape as Whisper's prompt-conditioning hallucination (see below) — a literal example sitting in the prompt got reproduced instead of a genuine extraction — just surfacing at the LLM few-shot layer instead of the STT layer. Fixed by dropping that example back to the original two neutral ones; re-tested and the hallucination is gone (that input now correctly returns `[]`).
- **Task #26 — tested and rejected a proposed STT prompt rewrite (reviewer feedback point 1).** External review suggested replacing `_STT_PROMPT` with a much longer bilingual version: meta-instructions ("transcribe exactly," "do not translate," "preserve code-switching"), ~3x the vocabulary in both languages, plus 5 full example sentences. Tested it head-to-head against the current prompt and no-prompt-at-all on three axes, all via the real Groq endpoint: hallucination rate on silence/noise/short-burst clips, transcription accuracy on the known-hard interleaved code-switch clip ("بدي احجز appointment الساعة three بكرة الصبح"), and the already-proven نعم (yes) fix. **Worse on all three**: silence hallucinated into long strings of invented, non-existent Arabic words plus stray cross-script garbage (vs. short recognizable filler under the current prompt, or generic "Thank you." with none at all); the hard code-switch clip came back with the entire sentence duplicated verbatim on every one of 5 runs (a classic Whisper repetition-loop, likely triggered by the inline example block); and نعم itself — the one thing the current prompt reliably fixes — came back garbled instead of correct. Root cause: Whisper's `prompt` is literal decoder context, not an instruction an instruction-tuned model obeys, so more text — especially structurally-similar example sentences — gives it more to loop on or hallucinate from, not less. **Rejected outright, no partial adoption.** Current `_STT_PROMPT` left unchanged.
- **Task #27 — built a real 62-utterance Arabic-English code-switch STT benchmark (reviewer feedback point 9), first real measured numbers instead of one-off spot checks.** Synthesized via ElevenLabs (production's own TTS), transcribed via the real production STT config (Groq `whisper-large-v3-turbo`, current `_STT_PROMPT`, unchanged after task #26), scored by exact-match and word error rate against the spoken ground truth. By category: pure Arabic 100% exact match (WER 0.000), pure English 60% (WER 0.229), clause-boundary code-switch 20% (WER 0.402), yes/no confirmations 40% (WER 0.425), single-word interleaved code-switch (no pause) **0% exact match, WER 0.564** — the worst category by far, and the reviewer's own 17-example list scored 5.9%/WER 0.625, similarly rough. Confirms with real numbers what spot checks only suggested: code-switching itself, not general STT quality, is the bottleneck — pure-language inputs are essentially solved, mixed-language inputs are not, and unpaused single-word interleaving is the worst case by a wide margin. **A second, independent instance of the نعم/booking-confirmation risk already flagged**: "no cancel it please" transcribed as `نعم، نعم، بكثير من الوصف.` — a genuine spoken "no" flipped to the literal word "yes," twice, in an otherwise fully garbled sentence. Different mechanism from the earlier silence-hallucination case (this one is a real mistranscription under code-switched/accented conditions, not a hallucination on non-speech audio) — two independent root causes converging on the same dangerous failure mode is worth taking seriously, though no fix has been scoped yet. **Real methodology caveat, not fully resolved**: many individual "failures" (e.g. `بدي كانسل الموعد` for a reference that wrote "cancel" in Latin script) may be TTS pronunciation artifacts rather than STT errors — there's no fixed convention for which script a spoken loanword should transcribe as, and the audio couldn't be manually verified by ear. The category-level pattern (pure-language solid, mixed-language collapsed, interleaved worst) is robust regardless; the precise 24.2% overall exact-match number should be read as "STT+TTS round-trip accuracy," not isolated STT accuracy. Full utterance list and per-item results in `/tmp/.../scratchpad/benchmark_utterances.py` and `benchmark_output.txt` (session-local, not part of the repo).
- **STT vocabulary-hint prompt can leak into the transcript itself.** Observed during the live production deployment test (browser → Vercel → LiveKit Cloud agent worker, real conversation, not a script-level test): on a garbled/low-quality Arabic utterance, the transcript came back as fragments of `stt_adapter.py`'s own `_STT_PROMPT` vocabulary hint ("نعم، لا، بكرا...") rather than what was actually said. Same underlying mechanism as the already-fixed "Sarjy"→"Sergey" mishearing — Whisper's prompt biases output toward the prompt's own content on ambiguous audio, not just the language/vocabulary it's meant to nudge — so the prompt engineering that fixed one failure mode can itself cause a different one (hallucinated content) on sufficiently bad audio. No fix applied yet; worth watching for recurrence on real microphone input (this was a synthetic/fake-capture-device test) before deciding whether the prompt needs trimming.
